# 2048 Duo 어드민 확장 기획서

작성일: 2026-10-16 · 갱신: 2026-10-17 · 상태: P0 로컬 구현 완료, P1/P2 제안

P0의 실제 제공 기능·설정·검증 경로는 [관리자 문서](admin.md#2026-10-17-p0-확장)를 기준으로 한다. 아래 일정·미결정 표는 최초 기획 당시의 기록이며, 원격 배포·DB 적용 완료를 뜻하지 않는다.

## 1. 목표와 핵심 판단

**현재 어드민은 완료 경기의 통계를 보고 계정을 정지하는 기본 도구다. 다음 단계는 운영자가 문제 경기를 찾고, 저장 장애를 구분하고, 조치 이력을 추적할 수 있게 만드는 것이다.**

대상은 초기 서비스의 운영자다. 운영자 1~3명이 게임 운영과 문의 대응을 겸한다는 가정으로 범위를 잡았다. 실제 운영 인원·사용량·문의 빈도·배포 상태는 확인되지 않았으며, 아래 우선순위와 일정은 이 가정을 바탕으로 한 제안이다.

첫 출시에서는 다음 세 가지 업무를 완결한다.

1. “이 경기에서 무슨 일이 있었나?” → 경기 ID 또는 사용자로 검색해 양측 결과와 Elo 변화를 확인한다.
2. “점수가 왜 반영되지 않았나?” → 서버 응답, 결과 저장 대기, 랭크 참가 제한 상태를 구분한다.
3. “누가 이 계정을 왜 정지했나?” → 전체 관리 이력을 검색하고 해당 사용자로 이동한다.

## 2. 현재 구현과 지켜야 할 경계

### 2.1 이미 있는 기능

| 영역 | 확인된 구현 | 추가 기획의 출발점 |
|---|---|---|
| 별도 관리자 앱 | `apps/admin`, 별도 로그인·쿠키·배포 구성 | 기존 앱을 확장한다. 게임 웹에 관리자 화면을 다시 만들지 않는다. |
| 접근 제어 | DB `admin_roles` 등록 여부를 화면과 관리자 RPC에서 각각 확인 | 권한 검사가 없는 상태가 아니다. 기존 검사를 신규 조회에도 적용한다. |
| Overview | 7·30·90일, 모드 필터, 완료 경기·참가 계정·평균값·종료 사유·티어·공격 통계 | 기존 데이터의 해석과 조사 연결을 개선한다. |
| Players | 이름·username·이메일·UUID 검색, 50개 단위 목록, 레이팅·가입일·상태 | 상태 필터와 검색 맥락 유지가 필요하다. |
| 사용자 상세 | 최근 20경기, 공격 집계·Elo 변화, 최근 20건의 정지/해제 이력 | 오래된 기록과 특정 경기 조사로 이어지는 경로가 없다. |
| 이용 정지 | 사유·확인창, 상태 변경과 감사 기록의 원자적 저장, 관리자 정지 금지 | 기간과 만료가 없는 정지/해제 방식이다. |
| 결과 저장 복구 | 디스크 outbox, 30초 간격 재시도, 경기 ID 중복 반영 방지 | 복구 기능은 있지만 어드민에서 상태를 볼 수 없다. |
| 검증 자산 | DB 권한·집계·정지·저장 재시도 테스트, 기존 브라우저 QA 기록 | 확장 시 기존 시나리오를 재사용한다. 이번 기획 작업에서 재실행한 것은 아니다. |

### 2.2 유지할 규칙

- 어드민에 Supabase 서비스 키를 추가하지 않는다. 사용자 세션과 DB 권한 검사로 필요한 기능만 제공한다.
- 완료 경기·Elo의 원본은 서버가 저장한 DB 결과다. 어드민 조회가 경기 결과나 점수를 바꾸지 않는다.
- 현재 서버는 단일 인스턴스이며 방·대기열은 메모리에 있다. 서버 재시작으로 사라진 미완료 경기를 기존 DB만으로 복구할 수 없다.
- 계정 정지는 신규 일반전·랭크전·친구전 참가에 적용한다. 진행 중 경기·재접속·항복은 유지하며, 게스트 재접속 차단까지 보장하지 않는다.
- 과거 공격 telemetry의 `NULL`은 미수집, `0`은 수집된 실제 0이다. 둘을 섞어 평균이나 비율을 계산하지 않는다.
- 현재 저장된 정보는 경기 종료 집계다. 입력 재생, 경기 중 보드 복원, 부정행위 확정 판정의 근거로 확대 해석하지 않는다.
- 기존 마이그레이션을 고치거나 데이터를 초기화하지 않는다. 필요한 변경은 새 마이그레이션으로 추가한다.

## 3. 부족한 점과 우선순위

P0는 첫 개선 출시, P1은 다음 운영 단계, P2는 수요가 확인될 때 진행한다. 영향·확신·작업량은 각각 1~5의 기획 추정이며, 참고 점수는 `영향 × 확신 ÷ 작업량`이다. 확신은 코드에서 확인한 결손에 대한 확신이며, 실제 고객 수요의 검증 정도는 아니다. 장애 대응과 데이터 접근 의존성을 점수보다 우선한다.

| 후보 | 현재 부족한 점 | 영향/확신/작업량 → 점수 | 우선순위·다음 행동 |
|---|---|---|---|
| 경기 목록·상세 | 전역 경기 검색과 양측 결과 비교가 없음 | 5/5/3 → 8.3 | **P0**: 기존 경기 테이블을 읽는 목록·상세 추가 |
| 서버·저장 상태 | `/health`는 `{ok:true}` 응답뿐이고 outbox 상태 UI 없음 | 5/5/4 → 6.3 | **P0**: 보호된 운영 상태 조회와 경고 표시 추가 |
| 전체 감사 이력 | 사용자별 최근 20건만 조회 | 4/5/2 → 10.0 | **P0**: 기존 `admin_audit`의 전역 검색 추가 |
| 사용자 탐색·표시 정리 | 상태 필터·검색 복원 부족, 지표명·시간대 혼동 | 3/5/2 → 7.5 | **P0**: 기존 화면과 RPC를 작게 확장 |
| 기간 비교·밸런스 분석 | 이전 기간·당시 실력별 비교 없음 | 4/4/3 → 5.3 | **P1**: 기존 데이터로 가능한 비교부터 추가 |
| 기간제 정지·이의제기 안내 | 만료 시각·자동 만료 판정·구체적 문의 경로 없음 | 4/4/3 → 5.3 | **P1**: 제재 기간과 공개 안내 정책 먼저 확정 |
| 신고·처리 대기열 | 이용자 신고 접수와 처리 상태가 없음 | 4/3/4 → 3.0 | **P1**: 접수·검토·종결의 최소 흐름 설계 |
| 관리자 인증 강화·권한 분리 | 앱의 MFA 강제 흐름과 역할별 권한 구분 없음 | 5/4/4 → 5.0 | **P1, 조건부 P0**: 외부 운영자 위임 전 적용 |
| 공지·점검 안내 | 배포 없이 이용자에게 운영 상황을 전달할 화면 없음 | 3/3/2 → 4.5 | **P1**: 단일 공지 배너부터 시작 |
| 리텐션·매칭 품질 | 완료 경기 외의 방문·대기·이탈 이벤트 없음 | 3/3/4 → 2.3 | **P2**: 먼저 이벤트 정의와 수집 필요성 검토 |
| CSV·외부 알림 | 데이터 반출·화면 밖 장애 통지 기능 없음 | 2/3/3 → 2.0 | **P2**: 보고·온콜 수요가 생길 때 범위 결정 |

작은 수정만 먼저 할 수 있다면 지표명·시간대·상태 필터·전체 감사 이력부터 시작한다. 다만 이것만으로 경기 조사와 장애 확인 업무가 완성되지는 않는다.

## 4. 첫 출시 화면과 업무 흐름

### 4.1 메뉴 구성

| 메뉴 | 역할 | 변경 |
|---|---|---|
| Overview | 완료 경기·밸런스 요약, 운영 경고 요약 | 기존 화면 개선 |
| Matches | 경기 검색과 양측 결과 비교 | 신규 `/matches`, `/matches/[id]` |
| Players | 사용자 검색, 상태·전적·제재 확인 | 기존 화면 확장 |
| Operations | 서버 응답·대기열·결과 저장 상태 | 신규 `/operations` |
| Audit log | 전체 정지·해제 이력 검색 | 신규 `/audit` |

현재 관리자 화면의 영어 UI는 유지하는 안을 기본으로 한다. 기획서의 한글 명칭은 설명용이다. 기존 디자인·공통 Button/AlertDialog를 사용하고, 모바일에서는 표 내부만 가로 스크롤한다. 상태는 색과 텍스트를 함께 표시한다.

### 4.2 P0-A — 경기 조사

**운영자가 할 일:** 문의에 포함된 경기 ID나 사용자 ID로 기록을 찾고, 두 참가자의 결과를 한 화면에서 비교한다.

- 목록 필터: 경기 ID 정확 검색, 참가 계정 UUID, 종료일 범위, 모드, 종료 사유. 사용자 이름 검색은 기존 Players를 이용해 대상 계정을 확정한 뒤 이동한다.
- 기본 조회: 최근 7일, 종료 시각 내림차순, 50건 단위. 동일 시각은 경기 ID로 순서를 고정한다. 날짜 검색은 KST이며 시작일 포함·종료일 다음 날 00:00 미만으로 처리한다.
- 목록 항목: 경기 ID, 종료 시각, 모드, 두 참가자 표시명, 승패, 종료 사유, 경과 시간.
- 상세 항목: 시작·종료 시각, 양측 점수·최대 타일·유효 이동·공격 충전/발사/수신, Elo 전후·증감, 사용자 상세 링크.
- 사용자 상세의 최근 경기 행을 경기 상세로 연결하고, “전체 경기 보기”는 해당 사용자 필터를 적용한다.
- 검색·필터·페이지를 URL에 보존해 새로고침과 뒤로가기 후 조사 맥락을 유지한다.
- `legacy` 모드를 그대로 식별한다. 연결된 계정이 없는 참가자는 “계정 연결 없음”으로 표시한다. `player_id = NULL`만으로 게스트와 삭제된 계정을 정확히 구분할 수 없다.
- 경기 ID가 없으면 “저장된 경기 없음”을 표시하고 Operations의 저장 대기 확인 경로를 제공한다. DB 부재를 곧바로 경기 유실이나 조작으로 단정하지 않는다.

**완료 기준:** 20건을 넘는 사용자 기록을 탐색할 수 있고, 한 경기의 두 참가자를 비교할 수 있다. 일반 계정의 직접 RPC 호출은 거부된다. 미수집 telemetry, 계정 연결 없음, `legacy`, 0건, 잘못된 UUID, 통신 실패가 구분되어 표시된다.

### 4.3 P0-B — 서버와 결과 저장 상태

**운영자가 할 일:** 경기 수가 줄어든 원인이 단순 저활동인지, 서버 접근 실패인지, 저장 지연인지 판단한다.

| 표시 항목 | 정의·수집 원천 | 주의점 |
|---|---|---|
| 서버 응답 | 현재 `/health` 응답 여부와 확인 시각 | 응답 성공이 DB·저장·게임 전체 정상이라는 뜻은 아니다. |
| 연결된 플레이 세션 | 서버가 관리하는 현재 연결 세션 수 | 사람 수·고유 회원 수와 구분한다. |
| 방 상태 | 준비 대기·플레이 가능·재접속 대기로 나눈 열린 방 수 | `rooms.size`를 그대로 “진행 경기 수”라고 부르지 않는다. |
| 매칭 대기 | 일반·랭크별 현재 대기 인원과 최장 현재 대기 시간 | 친구 코드 대기는 별도 수치, 완료된 매칭의 평균 대기 시간은 아님 |
| DB 저장 대기 | outbox의 대기 결과 수와 경기 ID, 가장 오래된 결과의 종료 후 경과 시간 | DB 반영 후 응답/파일 정리가 실패한 결과도 포함할 수 있음 |
| 랭크 재참가 제한 | 저장 대기 때문에 제한된 계정 수 | 파일 쓰기 자체가 실패할 수 있으므로 파일 수와 별도 집계 |
| 저장 경로 상태 | 최근 원격 저장 성공 시각, 파일 읽기/쓰기 실패 여부 | 프로세스 시작 후 성공 기록 없음과 저장 실패를 구분 |
| 데이터 신선도 | 서버 시작 시각·상태 수집 시각·화면 조회 시각 | 이전 프로세스의 상태를 현재 정상으로 표시하지 않음 |

기본 갱신은 화면이 보일 때 30초 간격과 수동 Refresh다. 일시적인 조회 실패 때 마지막 성공값을 남기되 “갱신 실패·마지막 확인 시각”을 표시한다. 정상적인 0, 수집 안 됨, 접근 거부, 조회 실패를 구분한다.

초기 경고 기준은 **제안값**이다. 2회 연속 갱신 실패, 결과 종료 후 2분을 넘긴 저장 대기, outbox 읽기/쓰기 실패를 경고한다. 운영 데이터로 조정하며, 관리자용 임계값 설정 화면은 만들지 않는다. Overview에는 경고 요약과 Operations 링크만 추가한다.

**접근 경계:** 관리자 앱의 서버 경로가 세션·DB 관리자 권한을 확인하고, 소켓 서버의 보호된 조회가 전달된 사용자 토큰과 관리자 권한을 다시 확인하는 구조를 제안한다. 공개 `/health`에 계정·방·outbox 내용을 넣지 않는다. DB 장애로 역할을 검증할 수 없으면 상세 상태도 접근을 거부하고, 공개 서버 응답 여부와 “상세 권한 확인 불가”를 분리한다. CORS만으로 보호하지 않는다.

첫 버전은 조회 전용이다. 기존 자동 재시도를 유지하고 강제 재시도·파일 삭제·점수 수정 버튼은 추가하지 않는다. 서버가 내려갔거나 디스크를 잃은 상황에서는 이 화면도 과거 상태의 복구를 보장하지 않는다. 장애별 확인 절차와 담당 경로를 운영 문서에 함께 적는다.

**완료 기준:** 정상·DB 오류·파일 읽기/쓰기 오류·미설정·서버 접근 실패를 구분한다. 저장 지연 후 기존 재시도가 성공하면 대기와 제한 상태가 갱신된다. 상태 조회가 경기 입력 처리를 막지 않으며, 서버가 재시작되면 이전 수치를 현재값처럼 보여주지 않는다.

### 4.4 P0-C — 전체 감사 이력과 사용자 탐색

- 전체 감사 이력에 기간·실행자 UUID·대상 사용자 UUID·정지/해제 필터, 50건 단위 페이지를 제공한다.
- 기록 시각·실행자·대상·행위·사유를 표시하고 사용자 상세로 연결한다. 삭제된 계정은 원본 UUID를 남기고 링크가 없음을 안내한다.
- 기존 `admin_audit`를 조회한다. 이 단계에서 새 감사 시스템이나 기록 편집/삭제 UI를 만들지 않는다.
- Players에 정상/정지/관리자 필터를 추가한다. 목록의 검색·필터·페이지를 URL에 보존한다.
- 사용자 상세에는 최근 완료 경기 시각을 표시할 수 있다. 이를 “최근 접속”으로 부르지 않는다.
- 이미 저장한 제재 사유는 내부 기록으로 유지한다. 이용자 공개 사유로 자동 전환하지 않는다.

**완료 기준:** 사용자별 20건 제한을 넘어 이력을 찾고, 실행자·대상·기간 조합으로 좁힐 수 있다. 검색 왕복 후 이전 목록 상태가 유지된다. 기존 정지의 사유 필수·중복 요청 처리·권한 재검사·관리자 보호 규칙을 유지한다.

### 4.5 P0-D — 통계 해석과 표시 수정

| 현재 표현/동작 | 개선안 |
|---|---|
| `Registered players` | “선택 기간 경기 참가 계정 수”에 맞는 명칭으로 변경. 전체 가입자 수가 아님을 설명 |
| 일별 데이터는 경기 있는 날만 반환 | 조회 범위에서 정상적으로 집계된 무경기 날짜만 0으로 채움. 조회 실패를 0으로 표시하지 않음 |
| 일별 집계는 KST, 상세는 브라우저 기본 시간대 | 관리자 날짜·시간은 KST로 통일하고 시간대를 명시 |
| 최근 N일은 현재 시각부터 N일 전까지의 범위 | 현재 이동 기간 방식은 유지하되 정확한 조회 시작·종료 시각 표시. 양 끝 날짜가 부분 집계임을 안내 |
| 현재 티어 분포가 기간 통계와 함께 배치 | 기존 “기간 필터와 무관한 현재 전체 분포” 설명을 더 가까이 표시 |
| 평균 경기 시간 | 준비·재접속 대기까지 포함된 경과 시간임을 표시. 순수 플레이 시간으로 부르지 않음 |
| 공격 승률·표본 표시 | 기존 표본 수·상관관계 설명 유지. 작은 표본으로 우열을 확정하는 문구를 쓰지 않음 |

**완료 기준:** 동일 데이터를 다른 기기 시간대에서 보아도 표시 시각이 같고, 미수집·실제 0·오류가 구분된다. 기간 경계와 참가 계정 수의 정의를 툴팁 또는 인접 설명으로 확인할 수 있다.

## 5. 후속 기능의 최소 범위

### 5.1 P1 — 비교 가능한 통계

이전 동일 길이 기간 대비 경기 수·참가 계정 수·경과 시간·종료 사유 비율을 비교한다. 비교 기간이 0이면 증감률을 무한대로 표시하지 않고 “비교 기준 없음”을 표시한다. `opponent_disconnected / 완료 경기 수`는 “연결 종료로 끝난 경기 비율”이며 전체 접속 장애율이 아니다.

랭크 경기의 실력 구간 분석은 저장된 `rating_before`를 사용한다. 현재 레이팅으로 과거 경기를 다시 분류하지 않는다. 공격 사용률은 `해당 공격을 1회 이상 발사한 참가 결과 / telemetry 수집 참가 결과`로 정의하고 모드·기간·표본을 함께 표시한다. 참가 결과는 고유 사용자 수가 아니며, 한 사람이 여러 번 포함될 수 있다.

패치 전후 비교가 필요해지면 경기 생성 시 규칙 버전을 고정해 결과와 함께 저장한다. 버전 없는 과거 데이터는 “버전 미상”으로 남긴다. 첫 단계에서 실시간 밸런스 수정이나 실험 배분 기능까지 만들지 않는다.

### 5.2 P1 — 기간제 정지와 신고 처리

기간제 정지는 1일·7일·30일·무기한을 초기 후보로 제안한다. 기간 목록과 공개 사유는 운영 정책 결정 사항이다. `suspension_expires_at` 같은 만료값을 추가한다면 **실제 신규 참가 검사에서 현재 시각을 기준으로 유효성을 판정**해야 한다. 주기 작업의 실행 여부에만 해제를 의존하지 않는다. 목록·상세·매치 생성 직전 검사도 같은 정의를 사용한다.

상태는 `정상 → 기간제/무기한 정지 → 만료/수동 해제`로 구분한다. 기존 정지는 무기한으로 보존한다. 만료를 최초 기록하는 방식을 선택할 경우 한 번만 기록하고 시스템 행위자를 식별한다. 연장·단축·수동 해제는 사유와 변경 전후 값을 기록하고, 두 운영자의 동시 변경은 충돌을 알려 재조회하게 한다.

신고는 게임 결과/기록 화면의 “문제 신고”에서 시작한다. 첫 버전은 로그인 사용자가 자신의 저장된 경기와 참가자를 지정해 사유·설명을 제출하는 방식이다. 계정 연결이 없는 상대의 신고는 경기 문제로 남기고 계정 제재로 자동 연결하지 않는다. 서버에서 본인 참가 여부·대상 참가자·입력 길이·중복·요청 빈도를 확인한다.

처리 상태는 `접수 → 검토 중 → 조치 완료/기각`이며, 검토 시작 시 담당자를 기록한다. 신고 상세에서 경기·사용자 상세로 이동하고, 제재 실행과 신고 종결은 각각 명시적으로 기록한다. 신고 횟수만으로 자동 정지하지 않는다. 공개된 이의제기 안내와 내부 메모는 별도 필드로 분리한다.

### 5.3 P1 — 관리자 인증·역할

현 상태는 관리자 여부를 구분하는 단일 권한이다. 앱 코드에는 MFA 등록·확인·추가 인증 강제 흐름이 보이지 않는다. 실제 인증 공급자의 운영 설정은 별도 확인이 필요하다.

외부 운영자에게 권한을 위임하거나 조회 전용 담당자가 생기면 이 작업을 P0로 올린다. 최소 역할은 조회자와 운영자로 시작하고, 조회자는 통계·경기만, 운영자는 계정 관리·전체 감사 이력까지 허용하는 안을 검토한다. 이메일·제재 사유·운영 상세의 열람 범위를 역할별로 확정하고, MFA는 화면과 실제 API/RPC 권한 경계에서 강제한다. 복구 절차를 갖춘 뒤 적용한다.

첫 단계에는 권한 부여 UI를 만들지 않는다. 기존 신뢰된 DB 관리 경로를 유지한다. 권한 회수는 다음 데이터 요청부터 반영되어야 한다.

### 5.4 P1 — 공지, P2 — 점검 제어·고급 분석

공지의 최소 형태는 단일 배너다. 제목·본문·노출 시작/종료·활성 상태를 저장하고, 초안 미리보기 후 게시한다. 관리자 변경 이력과 게임 웹 노출까지 한 작업으로 묶는다.

신규 매치 차단을 동반하는 점검은 별도 기능이다. 서버의 매치 생성 직전 검사, 기존 대전 유지, 적용 확인, 해제 및 설정 조회 실패 정책을 정한 뒤 구현한다. 프런트 버튼만 숨겨 점검이 적용됐다고 표시하지 않는다.

리텐션은 우선 “완료 경기에 다시 참가한 계정”으로 정의하면 기존 결과로 일부 계산할 수 있다. 방문자 DAU, 가입 후 첫 경기 시도 전환, 매칭 대기 이탈률은 새로운 이벤트가 필요하다. 게스트를 여러 세션에 걸친 동일인으로 추정하지 않는다.

CSV는 실제 정기 보고가 필요할 때 추가한다. 기본값은 집계 데이터로 제한하고, 개인정보 포함 내보내기는 권한·범위·감사 기록과 스프레드시트 수식 실행 방지를 함께 설계한다. 외부 장애 알림은 운영 채널과 담당자가 정해진 뒤 동일 장애 중복 알림 억제·복구 알림을 포함한다.

## 6. 데이터·인터페이스와 구현 영향 범위

다음 이름은 **신규 인터페이스 제안**이며 현재 존재하는 API가 아니다. 기존 호출을 깨지 않는 형태로 확장한다.

| 기능 | 입력 → 출력 계약 | 데이터·영향 범위 |
|---|---|---|
| `admin_matches`, `admin_match` | 기간·모드·사유·참가자·경기 ID·페이지 → 경기 목록/양측 상세 | `matches`, `match_participants` 재사용. 관리자 신규 페이지, 사용자 상세 링크, `schema/admin` 확장 |
| `admin_audit_entries` | 기간·실행자·대상·행위·페이지 → 감사 기록 목록 | 기존 `admin_audit` 재사용. 조회 RPC와 페이지 추가 |
| `admin_players` 확장 | 기존 검색·페이지 + 상태 필터 → 필터에 맞는 총수·목록 | 기존 기본 인수·응답 의미 유지. 신규 RPC 서명/권한 grant와 기존 호출도 확인 |
| 운영 상태 조회 | 관리자 세션 → 수집 시각·구성 상태·방/대기/저장 집계 | `state`, `server`, `ResultStore`, 서버 조립 진입점, 관리자 서버 경로·페이지에 영향 |
| Overview 표시 개선 | 기존 필터 → 지표 정의·정확한 기간·표시 시간대 | 기존 집계 유지, 필요한 기간 메타데이터만 추가 |
| 기간제 정지 | 대상·기간·사유·확인한 현재 상태 → 적용 상태·감사 이력 | 신규 마이그레이션, 제재 조회와 매치 생성 경로, 관리자·게임 안내·테스트 모두 영향 |
| 신고·공지 | 사용자/관리자의 허용된 입력 → 처리 상태·노출 결과 | 새 테이블·RLS·전용 변경 경로와 양쪽 웹 화면 필요 |

P0의 경기·감사 조회는 새 업무 테이블 없이 구현할 수 있다. 운영 상태는 현재 프로세스의 관측값을 제공하며, 이 단계에서 시계열 저장소·새 분석 플랫폼을 도입하지 않는다. 상태 조회 때마다 outbox 전체 파일을 반복 파싱하지 않도록 기존 저장 흐름과 제한된 집계를 재사용한다. 파일 접근 실패를 빈 대기열로 숨기지 않는다.

공통 계약은 다음과 같다.

- 조회 인수의 UUID·기간·정렬·페이지 크기를 서버/DB에서 검증한다. 첫 목록은 최대 50건, 기간 검색은 기본 7일·최대 90일로 제안하되 정확한 경기 ID 검색은 기간 밖 기록도 찾는다. 더 오래된 기록은 기간을 이동해 조회한다.
- 경기·감사 목록은 동일 시각에 ID를 보조 정렬 키로 사용한다. 새 목록은 커서 방식으로 페이지 이동 중 중복을 줄이고, 기존 Players의 offset 방식은 유지한다. “더 보기”와 “전체 건수”는 실제 API가 제공하는 정보에 맞춰 표시한다.
- 로딩·빈 결과·잘못된 입력·접근 거부·통신 실패·갱신 지연을 구분한다. 확인되지 않은 쓰기를 성공으로 표시하지 않는다.
- 읽기 실패는 사용자가 재시도할 수 있게 한다. 기존 정지 요청의 결과가 불명확하면 재조회 후 결정하는 흐름을 보존한다.
- 대량 테이블의 추가 인덱스는 대표 데이터의 조회 계획·응답 시간을 보고 정한다. 사전 측정 없이 캐시나 별도 데이터 웨어하우스를 추가하지 않는다.

## 7. 이번 확장에서 제외할 것

- 계정 삭제, 일괄 제재, Elo 직접 수정, 경기 결과 덮어쓰기: 되돌리기와 영향 추적 정책이 먼저 필요하다.
- 원시 입력·전체 리플레이 저장, IP/기기 기반 동일인 추정, 자동 부정행위 제재: 현재 데이터로 검증할 수 없으며 첫 운영 도구의 범위를 넘는다.
- 게임 규칙의 실시간 편집, 시즌·보상·결제 운영, 다중 서버 전환: 이번에 확인된 핵심 운영 공백을 해결하는 데 필요하지 않다.
- P0의 외부 이메일·메신저 알림, 개인정보 CSV, 관리자 역할 편집 UI: 수요와 권한 정책이 정해진 후 별도 진행한다.

## 8. 성공 기준과 검증 계획

아래 시간은 측정 결과가 아니라 출시 목표다. 구현 전 대표 시나리오의 현재 소요 시간을 기록해 개선 전후를 비교한다.

| 목표 | 제안 기준 | 확인 방법 |
|---|---|---|
| 문의 경기 조사 | 경기 ID를 받은 뒤 양측 결과 확인까지 1분 이내 | 정상·게스트·과거 미수집 fixture로 직접 수행 |
| 저장 장애 인지 | 화면이 열린 상태에서 다음 2회 갱신 이내에 경고 | DB/디스크 오류를 분리 주입. 외부 알림 SLA를 뜻하지 않음 |
| 관리 행위 추적 | 실행자·대상·기간으로 특정 기록을 찾고 사용자로 이동 | 20건 초과 이력·삭제된 계정 fixture |
| 해석 일관성 | 시간대 차이·미수집·무경기·부분 기간을 잘못 표시하지 않음 | KST 경계, 다른 브라우저 시간대, telemetry NULL/0 확인 |
| 권한 보존 | 비관리자는 신규 RPC·상태 경로에서 보호된 데이터를 얻지 못함 | 직접 호출, 권한 회수 후 재요청, 입력 검증 검사 |

P0 검증은 새 조회 권한·필터·페이지 이동·KST 경계와 운영 상태 실패 분기에 집중한다. 기존 20건 화면을 없애는 경우 그 제한을 가정한 테스트와 fixture도 수정한다. 기존 정지/해제·랭크 결과 중복 방지·outbox 재시작 복구는 회귀 확인한다.

브라우저에서는 목록 → 경기 → 사용자 → 목록 복귀, 로딩·빈 값·오류·권한 회수, 키보드 탐색과 확인창 포커스, 375/768/1440px 화면을 확인한다. 실제 운영 계정의 정지 상태를 테스트 용도로 바꾸지 않는다. 역할을 부여한 테스트 계정과 테스트 경기만 정리한다.

## 9. 미결정 사항

| 결정할 내용 | 현재 제안 | 진행에 미치는 영향 |
|---|---|---|
| 운영 인원과 권한 위임 | 초기 소수 운영자, 기존 단일 관리자 권한으로 P0 시작 | 외부 위임/조회 전용 담당자가 있으면 권한·MFA를 P0로 이동 |
| 운영 상태 서버 경로 | 관리자 세션과 소켓 측 재검증, 조회 전용 | 배포망 접근 경로·토큰 검증 방식을 구현 전 검토 |
| 경고 임계값 | 30초 갱신, 2회 실패, 종료 후 2분 저장 대기 | 임시값으로 시작 가능, 운영 측정 후 조정 |
| 제재 기간·공개 사유·이의제기 채널 | 기간 후보와 내부/공개 사유 분리 | P1 제재 출시 전에 결정 |
| 게스트 신고와 보관 기간 | P1은 로그인 사용자의 저장된 경기 신고부터 | 게스트 접수·새 신고/메모 데이터 보관·삭제 정책은 확정 후 확장 |
| 다국어 | 현재 영어 관리자 UI 유지 | 한국어 운영 화면이 필요하면 별도 범위로 산정 |

현재 DB 기록의 보관 정책을 이 문서가 변경하지 않는다. 새 신고·메모·시계열을 수집할 때는 항목별 보관 기간과 삭제 범위를 정하고 구현한다.

## 10. 실행 순서와 전달 상태

| 단계 | 산출물 | 추정 규모 |
|---|---|---|
| 1 | 표시 수정·사용자 상태 필터·전체 감사 이력 | 2~3인일 |
| 2 | 경기 검색·양측 상세·사용자 화면 연결 | 3~4인일 |
| 3 | 인증된 운영 상태 조회·서버/저장 진단·경고 | 4~6인일 |
| 4 | 통합 시나리오·권한/장애 검증·운영 문서와 배포 확인 | 2~3인일 |

P0 합계는 **약 11~16인일의 초기 추정**이다. 저장소에 익숙한 개발자 1명, 기존 배포 기반 사용, 디자인 재구축 없음, 각 단계 기본 테스트 포함을 가정했다. 인프라 권한 변경·실제 데이터량·운영망 구성·인증 강화가 추가되면 다시 산정한다. 확정 일정이나 성능 보장은 아니다.

DB 조회 확장은 하위 호환 마이그레이션 → 서버의 보호된 상태 조회 → 관리자 화면 순으로 배포한다. 문제가 생기면 신규 화면·경로를 비활성화하고 기존 조회·게임 흐름을 유지한다. 이미 쌓인 경기·감사 데이터를 삭제하는 롤백은 하지 않는다.

**전달 상태:** 경기 조사·감사 조회·표시 정리는 구현 착수 가능한 범위다. 운영 상태는 소켓 접근 경로와 인증 경계의 설계 검토 후 착수한다. 기간제 정지·신고·역할 분리는 9절의 해당 정책 결정 후 구현한다. P0를 먼저 출시하고 실제 문의·장애 사례로 P1 순서를 다시 정한다.
