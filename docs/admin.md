# 관리자 화면과 밸런스 통계

관리자는 모노레포의 별도 Next.js 앱 `apps/admin`이다. 로컬 주소는 `http://localhost:3100`이며 게임 `apps/web`의 `/admin` 경로는 제거했다. 같은 Supabase 계정을 사용하지만 관리자 앱에서 따로 로그인하고, `sb-2048-admin-auth` 쿠키로 게임 로그인과 세션을 분리한다. DB의 `admin_roles`에 등록된 계정만 접근할 수 있으며 이메일이나 사용자 수정 가능 metadata로 관리자 권한을 판단하지 않는다.

## 2단계 인증(MFA)

관리자 권한은 **인증 앱(TOTP) 2단계 인증을 마친 세션(aal2)** 에만 부여한다. `20261017200000_admin_mfa.sql`이 `is_game_admin()`에 JWT `aal` 클레임 검사를 추가하므로 모든 관리자 RPC, 피드백 RLS, Storage 업로드 정책, 소켓의 `/admin/operations` 토큰 검증이 같은 경계를 공유한다. 비밀번호만 통과한 세션은 DB에서도 관리자가 아니다.

- 로그인 뒤 콘솔 레이아웃은 세션 보증 수준을 확인하고 aal1이면 `/mfa`로 보낸다. 등록된 인증 수단이 없으면 QR 코드와 수동 입력 키를 보여 주고 6자리 코드로 활성화한다. 이미 등록했으면 코드 확인만 한다. 완료하지 못한 이전 등록은 새 등록 때 정리한다.
- `/api/operations`는 aal1 세션에 `403 mfa_required`를 반환하고 Operations 화면은 2단계 인증 필요 상태를 표시한다.
- Supabase 프로젝트의 Authentication → Multi-Factor에서 **TOTP가 활성화**되어 있어야 한다. 비활성화 상태면 등록 화면이 프로젝트 설정 안내 오류를 표시한다. 환경별로 운영·staging 프로젝트를 각각 확인한다.
- 마이그레이션 적용 직후 기존 관리자 세션은 모두 등록 화면으로 이동한다. 인증 앱을 분실한 관리자는 신뢰된 DB 관리 경로에서 `auth.mfa_factors`의 해당 사용자 행을 삭제한 뒤 다시 등록한다. 앱에는 복구 코드나 수단 삭제 UI가 없다.
- 검증: `apps/socket/tests/coin-ledger.test.ts`(aal1 거절·aal2 허용·JSON 클레임 읽기)와 `apps/admin/tests/server-pages.test.mjs`(aal1 리디렉션·`/mfa` 렌더링·`/api/operations` 거절). 실제 인증 앱 등록은 Supabase 호스팅 환경에서 브라우저로 확인한다.

## 코인 지급·차감

사용자 상세의 **Coins** 구역은 현재 잔액, 최근 거래 20건, 지급·차감 폼을 제공한다. `admin_adjust_coins(p_user_id, p_delta, p_reason)`는 관리자 권한을 확인하고 1~1,000,000 범위의 수량과 1~500자 사유를 요구한다. 지갑 행을 잠근 뒤 잔액을 바꾸고 `coin_transactions`에 사유·처리 관리자 ID를 기록한다. 차감은 현재 잔액을 넘을 수 없고 익명 계정은 대상이 될 수 없다. `admin_coin_history(p_user_id, p_limit)`는 잔액과 최신순 거래를 반환한다. 거래 내역 자체가 감사 기록이며 기존 `admin_audit`에는 추가하지 않는다. [코인 거래 내역](cosmetic-shop.md#코인-거래-내역)

새 체크아웃에서는 `apps/admin/.env.example`을 `.env.local`로 복사해 공개 Supabase URL과 공개 키만 설정한다. `pnpm dev:admin`으로 독립 실행하거나 루트 `pnpm dev`로 게임 웹·소켓과 함께 실행한다. 서비스 키는 관리자 앱에 넣지 않는다. 게임 헤더에는 관리자 링크가 없으며 별도 관리자 주소로 접속한다. 배포할 때도 `apps/web`과 `apps/admin`을 서로 다른 프로젝트와 도메인으로 연결한다.

현재 관리자 로그인은 이메일·비밀번호 방식이며 Google 전용 계정 로그인은 제공하지 않는다. 게임과 관리자는 각자 현재 세션만 로그아웃한다. 로컬의 포트 차이는 쿠키 보안 경계가 아니므로 운영에서는 별도 호스트와 HTTPS를 사용한다.

기록 페이지는 서버에서 권한을 확인하고 조회·렌더링하며 필터와 페이지 이동은 URL에 저장한다. 변경 폼과 Operations 갱신은 클라이언트가 담당한다. 공통 `getAdminAccess`는 React 서버 요청 안에서만 인증·역할 조회를 공유하고, 각 데이터 RPC도 권한을 검사한다. [페이지별 렌더링 경계와 회귀 검사](page-performance-boundaries.md)를 참고한다.

## 화면

- **Seasons:** 현재 시즌·전환 이력과 사유를 확인하고 새 시즌을 연다. [랭크 시즌](ranked-seasons.md)
- **Feedback:** 사용자 제보 목록과 계정 연결을 확인한다. [피드백](feedback.md)

- **Overview:** 최근 7·30·90일과 전체·일반전·랭크전·친구전 필터, 경기 수, 참가 계정 수, 평균 경기 시간·점수·이동 수, 일별 경기 수, 종료 사유, 모드 분포, 현재 티어 분포, 공격 종류별 통계.
- **Players:** 이름·이메일·계정 ID 검색, 50개 단위 목록, 레이팅·가입일·이용 상태.
- **Player detail:** 최근 20경기, 경기별 공격 통계와 Elo 변화, 관리 작업 이력, 사유를 남기는 이용 정지·해제.
- **Content catalog / 콘텐츠 관리:** 업적·보드 스킨·프로필 아이콘 추가·수정, 이미지 업로드, 가격·해금 조건 설정, 초안·공개·보관 관리. 기존 구매와 해금은 유지한다. 데이터 구조와 사용법은 [콘텐츠 관리 가이드](content-catalog.md)를 참고한다.

일별 집계는 Asia/Seoul 날짜 기준이다. 티어 분포는 현재 생애 Elo의 티어·최초 평가 상태 스냅샷이며 조회 기간의 과거 티어가 아니다. 참가 계정 수는 선택한 경기의 중복 제거 계정 수로, 계정 ID가 없는 게스트는 포함하지 않는다.

## 수집 기준

서버가 경기를 종료할 때 참가자별 집계만 저장한다. 원시 키 입력·IP 주소·기기 추적 정보는 추가 수집하지 않는다.

| 값 | 의미 |
|---|---|
| moves | 보드가 실제 바뀐 이동 수. 무효 입력 제외 |
| charged | 256·512 병합으로 발생한 공격 수. 대기열 초과·종료 이동에서 발생한 수도 포함 |
| sent | 서버가 상대 대기열에 넣은 자동 발사 수. 대기열 초과·종료 후 발사 제외 |
| received | 해당 보드에 실제 배치된 장애물 수. 도착 예정인 공격 제외 |

발생·발사·수신은 X와 하드 블록을 나눠 기록한다. 자동 공격 전환 전 기록의 charged는 보유량 증가, sent는 수동 발사 수였으며 과거 집계는 변경하지 않는다. 종료 시 아직 도착하지 않은 공격 때문에 발사와 수신 수량이 다를 수 있다. 게스트끼리의 완료 경기 역시 익명 참가 결과로 집계한다. 게스트에게 개인 경기 기록이나 Elo를 부여하지 않는다.

수집 전 기록과 이전 outbox에는 telemetry가 없다. 화면에서 미수집 표본으로 표시하고 공격·이동 평균의 분모에서 제외한다. `0`은 수집된 경기에서 실제로 해당 행동이 없었다는 뜻이다.

‘공격을 사용한 참가자의 승률’은 참가 경기 표본의 상관관계다. 실력이 높은 사람이 더 많은 공격을 발생시키는 효과 등이 섞이므로 공격이 승리의 원인이라는 뜻은 아니다. 표본 수·경기 모드·종료 사유와 함께 확인한다. 경기 시간에는 연결 대기와 일시정지 시간이 포함된다.

## 유저 관리

이용 정지·해제는 사유와 최종 확인이 필요하다. DB가 관리자 권한을 매번 확인하고 계정 상태 변경과 감사기록을 한 트랜잭션으로 저장한다. 본인이나 다른 관리자 계정의 정지는 허용하지 않는다. 계정 삭제·Elo 수동 변경·관리자 권한 편집 UI는 제공하지 않는다.

정지는 새로운 일반전·랭크전·친구전 참가와 로그인 계정의 새 솔로 시작에 적용한다. 대기 중이거나 친구 방을 만든 계정도 실제 매치 생성 전에 다시 확인한다. 진행 중인 경기, 항복과 재접속은 계속 허용한다. 조회 실패 시 로그인 계정의 새 경기 시작을 보류한다. 로그아웃 후 게스트로 플레이하는 것을 계정 정지만으로 차단하지 않는다.

## 관리자 최초 지정

회원가입과 이메일 인증을 완료한 비익명 계정의 UUID를 확인한 후, 신뢰된 DB 관리 경로에서 `admin_roles.user_id`에 등록한다. 서비스 키를 웹 환경이나 브라우저에 넣지 않는다. 계정이 없으면 관리자 권한 부여를 먼저 진행하지 않는다.

테스트에서 만든 관리자·일반 계정과 관리 이력은 검증 후 해당 테스트 데이터만 삭제한다. 실제 사용자의 정지 상태를 테스트 목적으로 변경하지 않는다.

## 운영 한계

멀티플레이 경기 중 서버 프로세스가 종료되면 미완료 경기는 집계하지 못한다. 완료 결과는 기존 디스크 outbox와 중복 저장 방지 RPC를 사용하므로 영구 볼륨이 필요하다. 솔로는 별도로 DB에 저장한 진행상황을 복원하며 미저장 변경은 유실될 수 있다. 게임 서버는 현재 한 인스턴스를 전제로 한다. Operations의 연결 세션 수는 현재 프로세스의 연결 수이며 고유 사용자 수가 아니다. 상태 조회가 이전 프로세스의 미완료 멀티플레이 경기를 복원하지는 않는다.

접근 제어는 [Supabase DB 함수 권한](https://supabase.com/docs/guides/database/functions)과 [Next.js 서버 권한 검사](https://nextjs.org/docs/app/guides/authentication)에 따라 화면과 데이터 호출에서 각각 확인한다.

## 확장 계획

현재 구현의 부족한 점과 추가 기능의 우선순위·화면·데이터·완료 기준은 [어드민 확장 기획서](admin-expansion-plan.md)에 정리했다. P0 경기·감사 조회와 운영 상태 화면은 아래와 같이 구현되어 있으며 P1/P2는 별도 제안이다.


## 2026-10-17 P0 확장

- **Matches:** 종료일 KST 범위(최대 90일), 모드·종료 사유·경기 UUID·플레이어 UUID 검색. 정확한 경기 UUID는 날짜 밖에서도 조회한다. 50건 커서 페이지와 양측 점수·타일·이동·공격·Elo 상세, 기존 사용자 상세에서 전체 기록으로 이동한다.
- **Audit log:** 기존 정지·해제 이력의 실행자·대상·기간·행위 검색, 50건 커서 페이지. 삭제된 계정 UUID를 보존하되 존재하지 않는 사용자로 링크하지 않는다. 시즌 전환은 별도의 시즌 이력에서 관리자·사유를 확인한다.
- **Players:** 정상·정지·관리자 필터와 검색·페이지를 URL에 저장한다. 사용자 상세에서 돌아올 때 목록 맥락을 유지한다.
- **Overview:** 참가 계정 정의와 실제 조회 기간을 표시한다. 성공적으로 조회된 무경기 날짜만 0으로 채우며 오류를 0으로 숨기지 않는다. 날짜·시간은 KST로 고정한다. 운영 경고 요약에서 Operations로 이동한다.
- **Operations:** 연결 세션, 준비/진행/재접속 방, 일반/랭크 매칭 수와 최장 현재 대기, 친구 코드 대기, 결과 저장 대기 ID, 랭크 제한 계정 수, 최근 원격 저장, 디스크 오류, 서버 시작·수집·조회 시각. 화면이 보일 때 30초마다 갱신한다. 실패 시 마지막 성공값을 남기고 오래된 값임을 알린다.

`20261017010000_admin_expansion.sql`을 기존 마이그레이션 뒤에 적용한 다음 소켓과 관리자 앱을 배포한다. 새 조회는 기존 데이터와 결과 저장 함수를 변경하지 않는다. `ADMIN_SOCKET_URL`은 관리자 앱의 서버 전용 환경변수이며 로컬 예시는 `http://127.0.0.1:4000`이다. 운영에서는 실제 소켓 주소와 HTTPS를 사용한다. 설정이 없으면 Operations에 미설정 상태를 표시한다.

관리자 서버 `/api/operations`는 사용자 인증과 DB 역할을 확인한 뒤 사용자 JWT를 소켓의 `/admin/operations`로 전달한다. 소켓도 토큰과 DB 역할을 매 요청 재확인한다. 둘 다 캐시하지 않고, 서비스 키를 관리자 앱에 전달하지 않는다. 공개 `/health`는 `{ok:true}`만 유지한다. 소켓은 인증 공급자를 호출하기 전에 연결 주소별 분당 20회로 제한하며 초과 시 `429`와 `Retry-After: 60`을 반환한다. 관리자 서버를 경유한 요청은 같은 서버 주소의 제한을 공유한다.

경고 기준은 2회 연속 갱신 실패, 종료 후 2분을 초과한 저장 대기, outbox 읽기/쓰기 실패다. 원격 저장이 성공했지만 응답 확인이나 파일 정리가 실패한 결과도 대기 목록에 남을 수 있다. 먼저 서버·DB 연결 및 영구 볼륨 읽기/쓰기 상태를 확인하고 기존 자동 재시도의 복구를 확인한다. 이 화면에는 강제 재시도·파일 삭제·점수 변경 기능이 없다. 파일 읽기 실패는 알려진 대기 수만으로 전체 유실 여부를 판단할 수 없음을 뜻한다.

검증은 `apps/socket/tests/admin-expansion.test.ts`(실제 PGlite SQL, 권한·커서·KST 경계·1만 경기·계정 삭제), `admin-operations.test.ts`(토큰 재검증·권한 회수·실패·방/대기열 분류·디스크 복구), 기존 관리자/결과 저장 테스트와 `apps/admin/tests/admin-expansion.browser.mjs`(격리 Next 앱·가상 로컬 인증 서버)로 수행한다. 브라우저 fixture는 실제 운영 계정이나 DB를 사용하지 않는다.
