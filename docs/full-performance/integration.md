# 전체 기능 통합과 배포 기록

기준일: 2026-10-17. 완료된 작업은 `codex/full-integration`에서 통합하고 staging 검증을 거쳐 main으로 승격한다. 공용 작업 폴더의 미완료 변경은 그대로 보존한다.

## 브랜치 구성

- `codex/full-integration`: 솔로·저장·친구/관전·일일 퀘스트·카탈로그·음향·문서의 통합과 배포 검증.
- `codex/all-page-performance`: 관리자 데이터 페이지, 게임 웹의 정적 구간과 상호작용 분리, 스켈레톤과 미리보기 지연 로딩.
- `codex/game-runtime-performance`: 서버 설정 조회 공유, 싱글 타이머 독립 갱신, 보드 memo, 실시간 조회 합치기와 비활성 탭 폴링 제한.
- `codex/integration-db`: 배포 이력 차이를 수렴시키는 후속 마이그레이션과 구매/업적 보존 회귀 검사.
- `codex/performance-measurements`: 프로덕션 빌드의 전 페이지 측정, 실제 두 브라우저 대전, 측정 원본과 보고서.

## DB 이력 처리

운영에는 과거 싱글플레이 생성 후 철회 이력이 있고 staging에는 최종 솔로 테이블과 카탈로그가 이미 존재했다. social SQL의 배포 버전명도 환경별로 달랐다. 실제 이력을 CLI로 별도 임시 폴더에 가져온 뒤 아래 후속 파일만 추가한다. 이전 migration을 재실행하거나 적용 이력을 재작성하지 않는다.

| 환경 | 추가 적용 순서 |
| --- | --- |
| staging | `180000_integrated_solo` → `180001_integrated_daily_catalog` → `180002_attendance_portrait` |
| production | `160000_content_catalog` → 같은 `180000`·`180001`·`180002` |

`180000`은 솔로 기록/진행상황과 신뢰된 결과 RPC를 추가하며 관리자 수정 draft를 보존한다. 업적 보상은 공개된 보상에 연결된 경우만 공개한다. `180001`은 일일 퀘스트와 카탈로그 컬렉션 업적을 연결하고 업적 INSERT 이전에 플레이어 잠금을 획득한다. `180002`는 수정하지 않은 초기 출석 아이콘만 새 경로로 전환한다.

기존 구매·지갑·장착·해금과 관리자 수정 내용의 보존을 fresh/staging/production 이력별 PGlite 회귀 검사로 확인했다. PGlite는 단일 연결이므로 실제 PostgreSQL 교착 상태를 재현한 결과는 아니다.

## 이미지

원래 Storage 이미지는 덮어쓰지 않는다. 새 출석 이미지는 `profile-icons/attendance-king-v2.svg`, 컬렉션 아이콘은 `profile-icons/achievement-king.svg`에 업로드한다. 업로드 후 바이트 해시를 확인한다. staging에서 새 파일 2개 업로드와 기존 파일 13개 일치를 확인했다. 운영에는 15개 파일을 새로 업로드하고 모두 바이트 해시를 검증했다.

## 검증 기록

- staging 후속 마이그레이션 3개 적용 완료. 공개 카탈로그에서 스킨 36개·업적 19개·프로필 15개 및 새 이미지 경로 확인.
- 로컬 업적/카탈로그 회귀 21개 통과. 통합 DB/이미지 회귀 10개 통과.
- 런타임 브라우저 회귀 2개 통과: 설정 서버 조회 재사용/실패 복구, 실시간 요청 병합/숨긴 탭 복귀.
- 전체 `pnpm test` 259개, 타입 검사, 린트 통과. 웹·관리자 production 빌드와 staging Vercel 3개 검사 통과.
- 설정 계정 전환/로그아웃, 서버 설정 전달/실패 복구, 요청 병합/탭 복귀, 공개/보유 카탈로그 보상, 튜토리얼·친구·관전 및 관리자 필터/페이지 이동/액션 브라우저 검사 통과.
- staging Fly 실제 랭크 검사 통과: 두 임시 계정의 이동·재접속·항복, 저장 완료 응답, 경기 기록과 1184/1216 Elo, Origin 제한, 일반 계정의 관리자 접근 거절. 소유한 검사 경기와 계정만 삭제했다.
- 실제 staging DB와 로컬 소켓을 연결한 솔로 검사 통과: 서버 재시작과 새 세션 이후 진행상황 보존, 두 모드·업적 8개·장착·랭킹·중복 출석. 이 검사는 Fly 재시작 검사가 아니다.
- 운영 후속 SQL 4개 적용 완료. 공개 카탈로그 스킨 36개·업적 19개·아이콘 15개 확인.
- 전후 각각 720개 페이지 로딩, 155개 실제 앱 링크 이동, 자연 종료 2경기·항복 2경기, 솔로 시계 2회, 초기 번들 39개 측정. [비교](comparison.md)와 [측정 방법](README.md)을 함께 읽는다.

## 배포 순서와 호환성

이번 변경은 **DB·이미지 → 소켓 → 웹/관리자** 순서다. 새 웹의 전역 친구 presence 연결은 spectator handshake를 사용한다. 구형 소켓은 이를 일반 플레이어 연결로 취급해 진행 중인 게임 연결을 끊을 수 있으므로 새 소켓을 먼저 적용한다. 새 소켓은 기존 웹 handshake도 처리한다.

출석·구매·경기 저장 RPC는 유지한다. 다만 구형 웹의 이미 열린 업적 탭은 새 컬렉션 업적을 처음 해금할 때 알림의 정적 이름 조회가 실패할 수 있다. 저장된 출석/보상은 보존되며 웹 갱신 후 새로고침하면 정상 표시된다.

staging은 PR #6의 `0b90df576e82f8642839f1f6c301efe6a8dbcbf7`을 배포했다. 11:36 UTC 검사 직전 활성 경기·랭크 대기열·결과 저장 대기는 모두 0이었다. 운영도 11:37 UTC 소켓 교체 직전 같은 상태를 확인했다. 확인용 임시 관리자 계정과 역할은 즉시 삭제했다. 현재 구조는 방 상태가 메모리에 있으므로 이후 배포에도 무중단 경기 복구를 보장하지 않는다.

운영 기능 승격 PR [#7](https://github.com/sean2474/2048/pull/7)은 `dbdc654fecec148d493b1ab6df53fe9d247e7ad8`로 main에 병합했다. Fly 이미지는 동일 제품 코드의 staging 통합 커밋 `0b90df5`에서 빌드했으며 staging `deployment-01M54T3ZP4943M49WFN598DMNN`, 운영 `deployment-01M54TEVGR8W4CC58ZEJ1H07KK`다. 두 환경 모두 기존 전용 볼륨을 유지했다.

운영 웹/관리자 Vercel 검사는 모두 성공했다. 운영 공개/게스트 페이지 14개가 HTTP 200이고 응답 HTML에 staging DB 주소가 없음을 확인했다. 관리자 비로그인 `/operations`는 실제 브라우저와 브라우저 User-Agent HTTP 검사에서 로그인 화면으로 이동했다. 기본 Python User-Agent의 첫 관리자 요청은 403이었으며 이를 애플리케이션 오류로 계산하지 않았다. 두 소켓 health는 200이고 운영 결과 outbox 파일은 0개였다.

## 실제 배포 환경 대전 측정

staging과 운영에서 각각 게스트 친구전 4회(데스크톱/모바일 에뮬레이션 자연 종료·항복)를 완료했다. 운영 최초 데스크톱 자연 종료 시도는 전환 중 숨겨진 DOM이 선택자와 중복되어 시작 전에 중단됐다. 최초 기록을 보존하고 보이는 입력만 선택하도록 측정 도구를 수정한 뒤 해당 1건만 재측정했다. 제품 코드 변경은 없었다. 운영 두 자연 대전의 자동 입력 플레이 시간은 66.34초/98.47초이며 사람의 평균 경기 시간을 뜻하지 않는다. 자세한 지연과 연출 시간은 [실제 네트워크 보고서](remote-results.md)에 기록한다.

실제 운영 자연 종료 화면을 데스크톱/모바일 크기에서 확인했다. 네트워크 측정이 끝난 뒤 두 환경의 결과 outbox 파일은 각각 0개였다. 운영 랭크 큐에는 검사 계정을 넣지 않았다.
