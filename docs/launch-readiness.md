# 출시 점검 기록

2026-10-23 KST 운영 환경을 기준으로 확인했다. 코드·자동 검사 완료와 실제 운영 검증을 구분한다.

## 가입·비밀번호 복구

운영 Supabase 프로젝트 `rbfujqjvkfdgaofztrdq`의 Site URL은 `https://www.2048duo.io`이고 이메일 확인이 활성화되어 있다. Redirect URLs에는 `https://www.2048duo.io/**`, `https://2048duo.io/**`, 관리자 도메인과 기존 Vercel 주소가 등록되어 있다. 설정은 조회만 했으며 변경하지 않았다.

새 테스트 계정으로 14:20–14:23에 다음 흐름을 완료했다. 기존 사용자 계정의 비밀번호는 변경하지 않았다.

1. 이메일 인증 전 로그인이 거절되는 것을 확인했다.
2. 실제 Gmail 받은편지함에서 가입 메일을 수신하고 확인 링크를 열었다.
3. 실제 운영 `/auth/callback`에서 PKCE 쿠키로 인증을 완료하고 로그인했다.
4. 비밀번호 복구 메일도 같은 메일함에서 실제 수신했다.
5. 운영 복구 콜백의 재설정 경로, `no-store`와 `no-referrer` 응답을 확인했다.
6. 복구 전용 PKCE 세션으로 새 비밀번호를 설정하고 이전 비밀번호 거절·새 비밀번호 로그인 성공을 확인했다. 테스트 세션은 전체 로그아웃했다.
7. 검사 전용 계정만 서비스의 계정 삭제 API로 정리하고 삭제 후 로그인이 거절되는 것을 확인했다.

검증은 실제 메일, 운영 HTTP 콜백과 Supabase SDK로 수행했다. 휴대폰에서 폼을 직접 조작한 검증은 아니다. 비밀번호·인증 코드·토큰은 저장소에 남기지 않는다. 공급자 측 링크 만료 시간은 이번 검사 범위에 포함하지 않았다.

**공개 가입 전 남은 조건:** 운영 프로젝트는 아직 Supabase 기본 이메일 서비스를 사용한다. 기본 서비스는 프로젝트 팀 주소에 수신자가 제한되고 현재 시간당 2건 제한이 있어 일반 사용자 가입용으로 사용할 수 없다. 사용자 소유 SMTP를 연결한 뒤 팀 외부 메일함으로 가입·복구를 다시 확인해야 한다. 이번 소유자 메일함 수신 성공은 이 제한을 해소하지 않는다. [Supabase SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)

## 소켓 도메인과 서버

`socket.2048duo.io`의 기존 CNAME은 `2048-socket.fly.dev`를 가리킨다. Fly에 해당 도메인의 인증서를 추가했고 Ready 상태와 `https://socket.2048duo.io/health`의 정상 응답을 확인했다. 인증서 만료 예정일은 2027-01-21이다. 운영 웹의 기존 fly.dev 연결 주소는 유지했다.

점검 시 운영 머신은 도쿄(`nrt`) 1대, 1GB 메모리이며 결과 outbox용 전용 볼륨을 사용한다. 방·매칭·솔로 세션은 프로세스 메모리에 있다. 단순히 머신 수만 늘리면 서로 다른 방 상태를 보게 되므로 2대 구성에는 요청 라우팅과 소유권 조정이 필요하다. 계획된 업데이트의 drain과 머신 장애 시 진행 중 경기 복구는 별개다.

## 웹 응답·검색·공유

점검 시작 시 운영 웹과 관리자에는 HSTS가 이미 적용되어 있었다. CSP, X-Frame-Options, X-Content-Type-Options는 없고 `x-powered-by: Next.js`가 노출되어 있었다. 공개 웹의 robots.txt, sitemap.xml, OG 이미지도 없었다.

이번 변경은 두 앱의 보안 헤더와 powered-by 제거, 공개 웹 metadata·robots·sitemap·1200×630 OG 이미지를 추가한다. 관리자와 staging은 색인에서 제외하며 공개 metadata 경로는 인증 세션 갱신을 실행하지 않는다. Next.js의 inline hydration 호환을 위해 CSP의 `unsafe-inline`을 유지하므로 엄격한 nonce 기반 CSP와 같은 보호 수준을 의미하지 않는다.

관련 테스트, SSR 회귀, 타입·린트·프로덕션 빌드와 로컬 프로덕션 HTTP 응답을 검증했다. 실제 배포 여부는 해당 커밋의 GitHub Actions `release-staging`·`release-production` 기록으로 확인한다. 배포 전 로컬 검증을 운영 반영 완료로 간주하지 않는다.

## 의존성

운영 의존성 감사(`pnpm audit --prod`)는 취약점 0건이다. 전체 감사에는 개발 의존성 `braces@3.0.3`의 high 1건이 남아 있다. 점검 시 npm 최신 버전도 3.0.3이며 수정 버전은 배포되지 않았다. 존재하지 않는 버전으로 override하거나 감사 결과를 숨기지 않는다. [보안 권고 GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)

## 실제 사용자 환경에서 남은 확인

- 최신 운영 배포로 실제 휴대폰 두 대에서 대전·재접속·결과 저장·보상·구매를 연속 확인한다.
- 장시간 능력·공격·Elo 밸런스를 플레이 테스트한다.
- 사용자 소유 SMTP 연결 후 일반 수신자 가입·복구를 확인한다.
- 2대 서버의 역할에 맞춰 배포·장애 전환과 저장 순서를 검증한다.

자동 검사나 두 브라우저 시뮬레이션을 실기기 확인으로 기록하지 않는다.
